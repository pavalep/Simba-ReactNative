B-005: TrueSheet ^3.11.11 → ^4.0.0-beta.15 (major bump)
========================================================
The latest tag is 4.0.0-beta.15 (no 4.x stable yet). Codegen
upgrade + modal styling refresh. The breaking change that hit
us is the boolean `scrollable` prop on `<TrueSheet>` was renamed

D-033: content:// URI shim for Android-14+ scoped storage
==========================================================
react-native-fs predates scoped storage and uses `java.io.File`
under the hood, which cannot read `content://media/external/...`
URIs returned by the MediaStore / SAF folder picker on
Android-14+. Pre-D-033 behaviour: `RNFS.readDir(content://...)`
threw an IOException that the existing catch silently swallowed,
producing a "library is empty" failure that looked like an
empty-scan result rather than a scoped-storage permission issue.

The fix is a JS shim at `src/infrastructure/nativeFs/index.ts`
that dispatches by URI scheme:
  - `file://` and bare absolute paths → RNFS (unchanged)
  - `content://` → throws `UnsupportedContentUriError` with a
    remediation hint pointing at Settings → Apps → SIMBA →
    Permissions → Files and media → "Allow all files access"

`metadataService.ts` now uses the shim and surfaces the
Android-14+ error via `onCorrupt({uri, reason:
'permission_denied', message})` instead of silently returning an
empty result set. `CorruptionReason` type extended with
`'permission_denied'`; `CorruptFile` interface gets an optional
`message` field for the hint text.

The other 4 RNFS call sites (logger.ts / artCacheService.ts /
useDownloadsScreen.ts) only operate on internal app dirs
(`DocumentDirectoryPath`, `CachesDirectoryPath`,
`/data/data/com.simba.player/`) which are always `file://` on
the app's own storage and don't need the shim — they continue
to use RNFS as-is.

Future scope (post-manager-demo): replace the `content://`
shim branch with a Kotlin `MediaStoreFsModule` that wraps
`ContentResolver` and exposes `listDir` / `stat` to JS under
the same shim interface. Today's shim is the contract that
future native implementation will satisfy — the metadataService
caller surface stays unchanged.
