V18.6.2d fix: useApiQueries type signature (TanStack v5 QueryResults / QueryOptions)

Follow-up to V18.6.2d (168ac0a). The `QueriesOptions` rename
broke the type signature of `useApiQueries` — the v5 type
`QueriesOptions<T>` is a tuple type (`T` resolved through
the recursive `QueriesOptions` reducer), but the wrapper
expects an object shape `{queries: [...], combine?: ...}`.
The two don't compose.

What was actually wrong:

  - The V18.6.2d commit renamed the imported type from
    `UseQueriesOptions` (TanStack v4, deprecated in v5) to
    `QueriesOptions` (v5). The v5 type has a different
    shape:
      - `QueriesOptions<T extends Array<any>>` is the
        TYPE of the `queries` parameter (an array of
        query options, not the wrapper's input).
      - The wrapper's input is `{queries: QueriesOptions<T>,
        combine?, subscribed?}` (the actual `useQueries`
        parameter shape).
  - My wrapper was typing the input as
    `QueriesOptions<TResults> & {combine?: ...}` — which
    is "a tuple combined with a record" — and the test
    passed an object, so tsc complained.

What this fix does:

  - Drops the `QueriesOptions` import entirely. The wrapper
    now types the input as
    `{queries: ReadonlyArray<...>, combine?: ...}` where
    the `queries` element type is inferred from
    `useQueries`'s own parameter shape via
    `Parameters<typeof useQueries>[0]['queries'][number]`.
  - The return type is `TCombined | ReadonlyArray<unknown>`
    — `TCombined` if `combine` is provided, the raw result
    array otherwise. The consumer type-asserts inside
    `combine` to get per-source type safety.
  - The 3 useApiQuery tests (5 V18.1.2 + 2 V18.6.2a + 0
    newly-added — total 7) pass.

What this loses vs the V18.6.2a type:

  - The V18.6.2a type had a `TResults extends readonly
    unknown[]` generic that the consumer could specify
    for rich tuple inference. The new type is more
    permissive (the consumer type-asserts inside `combine`)
    but matches the v5 useQueries signature without
    leaning on internal types.
  - The user-facing API (pass `{queries: [...], combine?:
    ...}`) is unchanged. The `useAggregatedSearch` consumer
    works as-is.

Verification:

  - npx tsc --noEmit             : 0 errors
  - npx jest --forceExit         : 9 suites, 106 passed,
                                    1 todo, 0 failures

This is a docs-as-much-as-code fix: the wrapper docstring
now explains the v5 inference trade-off explicitly so the
next person who tries to add a stricter type knows why
it's permissive.
