V18.7.3: useDownloadsSync audit — confirmed out of scope (no change to logic)

V18.7.3 — the last V18.6 carryover item. Audits
`useDownloadsSync` per the V19 carryover list ("likely
no change needed — AsyncStorage hydration, not a network
query").

The audit conclusion (no code changes; the file gets a
doc-comment update that documents the "why"):

  - `downloadService.ensureLoaded()` reads from AsyncStorage
    (the offline-first manifest of completed downloads).
    This is NOT a network call. AsyncStorage is a local
    key-value store, not a wire protocol.
  - `downloadService.subscribe(records => ...)` is a
    pub-sub for progress events (a download in progress
    publishes its updated record; the store hydrates on
    each event). This is NOT a TanStack cache concern.
  - Neither maps to the V18 wire / query / screen 3-layer
    architecture. The hook is correctly outside V18's data
    layer refactor.

The V18 wire/query/screen layers are for HTTP adapters
that fetch from a network and cache the result. The
downloads slice is for the offline-first manifest: it's
the local state that mirrors what AsyncStorage already
has. TanStack's `useQuery` would be a downgrade here —
AsyncStorage is the source of truth, not a cache; the
hook's job is to load it once on mount and subscribe to
progress events thereafter.

V18.7.3 doc-comment update (in the file, not in this
commit message): the hook now has a paragraph that
documents this — "this hook is **not a network query**.
downloadService.ensureLoaded() reads from AsyncStorage
... neither maps to the V18 wire / query / screen 3-layer
architecture; the hook is correctly outside V18's data
layer refactor."

This makes the "no change needed" decision explicit so
the next person who looks at this file knows not to try
to migrate it to `useApiQuery`.
