V18.2.2: 19 unit tests for the weather convertors

Per the type contract §2.6, every convertor gets a unit test
with at least 3 cases (happy path, missing fields, undefined
input). This file exceeds the spec:

- cityCoordsFromRaw: 5 tests
  - happy path
  - results missing
  - results empty
  - non-numeric latitude (defensive boundary check)
  - undefined input (transport-failure case)

- weatherSnapshotFromCurrentRaw: 8 tests
  - happy path
  - temperature rounding (28.4 -> 28, 28.6 -> 29)
  - is_day=0 -> clearNight
  - current missing
  - temperature_2m missing
  - weather_code missing
  - undefined input
  - context fields pass through verbatim (source/cityName/fetchedAt)

- wmoCodeToCondition: 6 tests
  - code 0 + day -> sunny
  - code 0 + night -> clearNight
  - code 2 -> partlyCloudy
  - code 61 -> rainy
  - code 71 -> snowy
  - unknown code -> cloudy fallback

Total: 19 tests, all green. No HTTP, no axios — pure convertor
unit tests. The HTTP layer is exercised in V18.2.4 via the
migrated useWeather hook.

This is the keystone of the convertor pattern: when a screen
shows wrong weather data, the FIRST place to look is the
convertor test for the missing/malformed field. The tests
make debugging "the API changed" vs "the wire shape changed"
trivial.
