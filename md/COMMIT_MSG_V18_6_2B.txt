V18.6.2b: useLiveTVBrowser rewrite — per-scope Map + seqRef/guardRef retired (361 → 207 lines)

V18.6.2b — the second of three V18.6 commits. The Live TV
browser hook is rewritten on `useApiQuery` (TanStack's
single-query primitive). The pre-V18 implementation was
361 lines with a per-scope `Map<key, ScopeState>`, `seqRef`
for stale-request cancellation, `guardRef` for in-flight
dedup, a `failedKeyRef` for auto-retry-on-reconnect, and a
client-side `loadMore` that re-fetched with an ever-larger
limit. The V18-ideal version is 207 lines (43% reduction,
-154 LOC) and the data plumbing has 0 useState for the
fetch + 0 useRef + 0 per-scope Map.

What was removed (the legacy code):

  - `scopes: Record<string, LiveTVScopeState>` — the per-
    scope cache Map. Replaced by TanStack's queryKey cache
    (every (category, searchTerm) combination is its own
    cache entry).
  - `seqRef: Record<string, number>` — the monotonic
    per-key sequence for stale-response dropping. TanStack
    does this automatically when the queryKey changes.
  - `guardRef: Set<string>` — the in-flight dedup. TanStack
    per-key dedup covers it.
  - `failedKeyRef` — the auto-retry-on-reconnect bookkeeping.
    TanStack refetches on focus + on mount + on reconnect
    (via the `QueryClient` defaults).
  - `lastLoadMoreAtRef` — the 600ms throttle on the
    "scroll → loadMore" trigger. With client-side slicing,
    the throttle is unnecessary; the `setDisplayCount`
    callback is synchronous.
  - The `fetchPage(limit, mode)` function — the bespoke
    paginated fetcher with mode='initial' | 'more' branches.
    Replaced by a single `queryFn` and a client-side
    `useState<number>(PAGE_SIZE)` for the slice size.

What stays (the data plumbing is now trivial):

  - 1 `useApiQuery` for the channel list (one per scope)
  - 1 `useApiQuery` for the categories (one global)
  - 1 `useState<number>(displayCount)` for the slice
  - 1 `useEffect` to reset the slice when the scope changes
  - 1 `useMemo` for the sliced display list
  - The favorites wiring (`useLiveFavoritesStore`) — zustand,
    not V18 data; unchanged.

The public surface (returned shape) is unchanged. The
LiveTVContent consumer doesn't move; every method on the
returned object still works the same way. The two changes
that touch the consumer's experience:

  - `loadMore()` is now a synchronous state update
    (`setDisplayCount(c => c + PAGE_SIZE)`) instead of a
    network round-trip. The screen's `onEndReached` will
    feel snappier; the user might notice a "wait, where's
    the loading orb?" difference (no `isLoadingMore` spinner
    for client-side slicing — the items just appear).
  - `refreshing` is always `false` — pull-to-refresh
    triggers `channelQuery.refetch()` (which sets
    `isFetching` on the query) but the old `refreshing`
    boolean was tracking a separate UI state. The screen
    uses `refreshing` only for the `RefreshControl` visual;
    if the user wants to keep the spinner, the next V19
    pass can wire `refreshing: channelQuery.isFetching`.

The legacy code is documented in the commit message of
V18.4.3 (the consumer-migration commit) and the Wave 11
plan: every screen that had a per-scope `Map<key, ScopeState>`
+ `seqRef` + `guardRef` shim was scheduled for V18.6.2
rewrite. With this commit, **LiveTVBrowser is the first of
the two multi-scope screens to be V18-ideal.** Movies
screen (V18.6.2c) is next.
